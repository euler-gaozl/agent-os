# Windows 单机交付计划

更新：2026-10-12。用户最新优先级：先完整规划，在现有 Windows 电脑上完成可以日常使用的单机版，再推进服务器阶段。本文件是执行顺序和验收范围的权威；历史测试证据继续保留，不因修改规划而变成新版本的通过结果。

## 1. 当前目标与完成定义

交付一个可维护的本机 Agent 平台：统一中台管理自定义 Agent、提示词、Skill/MCP、资料、工作记忆与运行记录；独立期货工作台调用已发布 Agent；使用用户现有 DeepSeek 官方配置和固定版本的官方 DSH，完成有来源、有原文、可回查的研究工作流。用户做预测与交易决定，平台不以价格走势解释基本面。

“跑通”同时要求：从本机停止状态按一个明确入口启动；真实模型和工具完成业务任务；中断后恢复；原资料和调用回执保留；服务分别升级与回滚；备份能在隔离库恢复并核对内容；界面完整可用。不以端口可访问、目录数、截图或 CI 的绿色图标代替这些结果。

先复用已经验证的能力并修正真实缺口，不重写已通过的功能。单机同样保留独立服务、独立凭证、数据所有权和两个 Worker，不把个人部署重新合成单体。单机进程接管不等于整台机器故障时高可用。

## 2. 范围分层

| 范围 | 本阶段决定 |
| --- | --- |
| Windows 本机平台、共享管理 Web、独立业务 Web | 必须交付和本机验收 |
| 每个服务独立源码仓库、构建、配置、部署和迁移责任 | 必须落实，不只移动文件；允许明确版本的公共协议和同数据域库 |
| 真实 DeepSeek + DSH、知识原文引用、MCP/Skill 检测、任务恢复、记忆与证据留存 | 必须覆盖真实用户工作流；mock 与真实供应商结果分列；DSH 源码纳管与存储策略见下文 |
| 日常资料导入、采集、交叉核验、供给/库存研究 | 先完整验收一个真实业务样例；样例通过不能表述为全品种数据覆盖 |
| 全中国期货品种与长历史数据 | 保留为后续业务资料建设目标。按数据源覆盖矩阵逐批扩展，与平台是否可用分别验收 |
| 2 核 4 GB 服务器预算、百万文档/千万块 | 保留现有 Linux 测量与容量证据，最终目标规模的整体验收放后续；本机另记录真实资源消耗 |
| 跨机器 HA、数据库主备、机器宕机切换、公网生产部署 | 本阶段明确不做，不等待服务器，不计为单机版未完成项 |
| 多用户组织权限与租户、任意插件可信签名供应链、大规模生产运维 | 后续能力；本阶段是本人使用，仍必须有服务身份、边界鉴权、凭证保护和危险执行隔离 |
| Milvus、LightRAG、Langfuse、任意代码 Sandbox | 作为具备清晰依赖的扩展服务逐项验收。未配置的扩展不能显示为可用。核心资料流程以本机能运行的检索方案起步；没有隔离执行环境时禁止宿主机执行，不把禁用算作沙箱已完成 |

本机当前 PATH 中未发现 Docker，Sandbox 未配置镜像与 daemon；WSL 命令存在不证明已安装可用 Linux 环境。先完成只读探测，容器环境是否适合本机、是否需要系统功能/重启另作明确决定。不能把这个本机依赖问题归咎于没有服务器。已有 Linux CI 沙箱结果不能替代 Windows 的实际沙箱能力。

服务交付和扩展能力分开记录：12 个服务均须有独立仓库、构建、配置、迁移责任和兼容发布检查；同一服务的两个 Worker 实例不算两个服务。未配置 Sandbox 或 Langfuse 时，只能验收对应服务启动、状态和明确拒绝/降级，不能将隔离执行/遥测导出标记为可用。第一条本机核心路径明确使用 PostgreSQL 的 `Engine=local` 词法检索、Go 服务、固定 Node/DSH、两个 Worker 和两个 Web；不隐式把 Milvus/LightRAG 失败改成词法检索后声称原引擎成功。

目标目录：

```text
      agent-os-registry\
      agent-os-toolhub\

      agent-os-worker\
      agent-os-knowledge\
      agent-os-indexer\
      agent-os-storage\
      agent-os-sandbox\
      agent-os-telemetry\

      data\                      数据库与持久化资料

      backups\

      source-split-draft\        未验收拆分草稿，不能当正式仓库
    ops\                        本机运维入口/索引，通用实现归集成仓库
```

目录迁移分两步：先让运行配置和运维脚本支持显式工作区/数据根路径并兼容旧路径，再在有恢复证据的维护窗口搬迁。不能在运行中直接移动 PostgreSQL 数据目录，也不复制/重新初始化一个空库冒充迁移。2026-10-12 已通过这两步：有效源码为 `D:\workspace\agent-platform\repos\agent-os`，原数据库为 `local\data\postgres`。历史阶段记录中的旧路径保留其当时含义。

Runtime 仓库拥有执行域与其窄 `execution` 包；Worker 独立仓库按固定版本消费该包，保持 lease/fence、调用回执、笔记与调用效果的事务原子性。Knowledge 拥有知识 schema 与索引协议/库；Indexer 独立仓库消费固定版本，不能另造一套迁移。二者都不能引用另一个服务的启动入口或全部路由。

每个服务仓库要有自己的依赖锁、构建说明、配置契约、迁移拥有者、测试和 CI。集成仓库锁定各提交/镜像/协议版本；独立构建必须在只检出本仓库、`GOWORK=off`、没有 `../` 替换依赖的环境通过。私有模块/镜像只配置所需读取权限，凭证不得进入 Git URL、源码或 Docker 镜像层。

## 4. 实施顺序与关卡

| 阶段 | 实施内容 | 进入下一阶段的证据 |
| --- | --- | --- |
| P0 基线与计划 | 固定已验证提交；清点本机进程、构建、数据、配置引用和依赖；建立当前缺口矩阵；备份并隔离恢复；独立评审本计划 | 可重复的脱敏基线报告；资料计数/哈希；可恢复旧版本；计划评审问题已处理 |
| P1 本机运行底座 | 将源码与本机状态路径解耦；统一 `start/status/stop/doctor/backup/restore-check/update/rollback` 入口；检查进程归属、日志、端口与缺失依赖；分阶段迁至分组目录 | 移动源码不重建数据库；重复启动不生成重复实例；停止只操作本平台进程；冷启动和失败提示可验证；旧入口有明确迁移提示 |
| P2 真正拆仓 | 先 Registry/Sandbox/Telemetry；再其余已独立服务；最后拆 Runtime/Worker、Knowledge/Indexer 的代码与迁移边界；公共 SDK 删除跨域 SQL 与整个平台政策；分别配置私有仓库和 CI | 各仓库独立构建；禁止跨服务实现引用；每个服务迁移只改自身数据域；升级一个服务无需重新编译或替换其他服务；旧任务/资料继续可读 |
| P2.5 Harness 存储与上下文 | 维护固定 DSH 源码；实现持久化/checkpoint、结构化任务工作状态、Compact 固定信息与回查、长输出外置和缓存生命周期；按测量结果补必要 Session/Loop 接口 | 原始证据先持久化再确认；摘要不能覆盖任务权威状态；检查点失败阻止后续副作用；长任务内存/恢复测量与新旧引擎兼容测试通过 |
| P3 功能与界面闭环 | 中台 Agent 配置、绑定、发布和试运行；ToolHub 注册/导入/校验/验活/停用；资料上传/索引/引用；工作记忆和运行详情；业务端按业务问题使用；修复逐页发现的问题 | 真实浏览器逐页桌面/窄屏验收；用户完成操作无需懂 MCP/Skill；完整真实 DeepSeek + DSH 工作流，原文与报告引用可回读 |
| P4 故障和恢复 | 双 Worker 接管、任务取消、工具失败/超时/丢回复、模型断连、Compact 后回查、记忆冲突、数据库暂失、进程重启、备份还原、单服务回滚；重现混合负载失败并保存诊断 | 每个场景有输入、版本、故障位置、结果与原始证据；不重复执行已完成效果；无法确定的外部效果明确待核对；失败原因未明则仍列缺陷 |
| P5 日常使用验收 | 以一个真实期货供给/库存任务走资料采集→校验→入库→研究→回查→继续任务；完成本机资源/连续任务测量和维护说明；独立复审 | 按下面矩阵全部完成核心项；扩展项单列真实可用性；交付固定版本、入口、运行手册和仍未做的下一阶段清单 |

阶段可以在没有依赖的地方并行准备，但不得跳过关卡切换本机正式版本。每次实施围绕一个阶段交付可验收增量，不因聊天新增一个名词就立即引入框架或重写架构。

P0 的恢复集合必须先覆盖所有权威数据库，而非只备份一个 `DATABASE_URL`；同时包括受保护的配置/加密密钥、服务与 Harness 固定版本、必要运行产物和引用。清单只存位置/摘要/恢复次序，不含秘密值。涉及多库时，最简单的单机一致性方案是在维护窗口停止写入后备份。隔离恢复环境禁止自动执行遗留任务或调用真实外部写入工具。

P4 逐场景记录 Windows 的实际动作（如按所属进程强制终止 Worker）、恢复点、数据库断言和证据位置；核对遗留 Node/Harness 子进程与旧 fence，而不是以 Linux SIGKILL 测试代替本机测试。模型故障矩阵优先用受控供应商，真实 DeepSeek 只补业务链路的必要验证。

P5 执行前固定一个品种、日历日期区间和供给/库存核心问题；验收关键指标的原始来源、发布日期/统计期、单位/口径、交叉核验与冲突说明。每个报告引用能回读保存的原文；资料不足可以得出“证据不足”，不能以模型生成内容补数。

DSH 专项依据与修改边界见 [源码与存储系统决策](architecture/dsh-source-and-storage-decision.md)。源码可维护不意味着必须改核心：已有扩展点能完成的持久化与压缩策略使用自有插件；同一会话分页历史、检查点恢复的必要核心改动必须由具体压力/恢复测试证明。旧任务继续使用原引擎，禁止直接切换 native resume 后丢失既有成功回执的语义。

## 5. 核心验收矩阵

| 编号 | 验收场景 | 必须看到的结果 |
| --- | --- | --- |
| W01 | 本机冷启动、重复启动、停止、重启 | 操作入口稳定；正确识别已有进程；资料保留；缺失依赖指出具体解决方式 |
| W02 | 各服务独立构建/升级/回滚 | 记录服务版本和配置摘要；非目标服务身份与版本不变；不兼容版本在替换前拒绝 |
| W03 | 新建自定义 Agent，绑定提示词、Skill/MCP、知识库并试运行 | 不可变版本生效；运行固定原配置；配置更新不偷偷改变已提交任务 |
| W04 | 上传正常/错误 Skill，注册可用/失效 MCP，停用正在使用的工具 | 安全校验和可读错误；验活有最近检测时间；停用后新执行受控；不把 metadata 声明当安全证明 |
| W05 | 上传资料、重传、索引、搜索、原文回读与失效后检索 | 去重、状态和来源清楚；资料/Agent 权限生效；不伪造“已索引”；支持格式明确列出 |
| W06 | 官方 DeepSeek + 固定 DSH + 业务工作台 | 至少一个真实多步任务完成模型→工具→落盘→回读；区分事实/计划、日期/口径/引用，不做价格预测 |
| W07 | 两个 Worker 中断一个，恢复既有任务 | 新 lease/fence 接管；旧实例不能提交；完成回执不重做；真实效果不因重试重复 |
| W08 | 超长任务触发 Compact，中断后继续 | 原始证据落盘；回执目录与原文可查；摘要遗漏不能造成唯一证据丢失 |
| W09 | 笔记修订/撤回/过期/并发冲突 | 原文与审计保留；新视图正确；冲突明确反馈；不任意挑选历史分叉；不自动删除正式资料 |
| W10 | 网络/模型/工具异常与不确定结果 | 有界重试；已知拒绝与未知效果区分；界面显示可采取的下一步，不假报成功 |
| W11 | 备份后恢复至独立测试库 | 不只检查 dump 文件；实际恢复并核对资料、哈希、引用、任务/笔记状态；恢复失败保持原库不变 |
| W12 | 安全与资源 | 密钥不进代码/日志/报告；跨服务/跨 Agent 访问拒绝；采集有边界；记录整体进程和数据库实际资源及测量工作负载 |
| W13 | 全部中台和业务页面 | 桌面与窄屏可操作；加载/空/失败状态明确；表单、列表、详情和运行输出可读，业务端不暴露基础设施术语 |
| W14 | 源码 Harness 的存储与内存策略 | 固定构建可复现；事件/flush 屏障失败可见；结构化工作状态不靠摘要独占；大输出按引用分页；内存与恢复耗时经过递增长历史测量；不破坏旧任务 |

对于历史测试已覆盖的场景，先判断是否因改动失效；只有与当前提交及部署组合一致的证据可以沿用，迁移/源码边界变化后必须重新验证相关场景。日常冷启动先用实际停止再启动验收；未经用户参与的整机重启/断电不声称已测。
