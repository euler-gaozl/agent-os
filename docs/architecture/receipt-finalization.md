## 问题和边界

真实 native-v4 任务在第十、十一轮送检，第十二轮又改写了 questions，尽管 facts 保持不变。因此“最后送检稿逐字输出”的提示词没有提供保证。新稿应引用已持久化原文交付，不应依靠模型复制数万字，也不能静默把旧任务 raw result 替换成旧草稿。

当前 Futures 已并列显示最终回答、历史送检稿和一致性提示。这是读取能力，不是确定性成稿协议。旧任务 completed/result、native-v4 与历史 finish 协议全部保持；需要修改循环或重放可见行为时使用新的固定引擎。

## 实施职责

1. 在任务创建时冻结通用最终产物策略：允许的工具、固定输入字符串字段和策略版本。业务侧配置绑定具体检查/提交工具，核心 Runtime 不识别期货 schema 或检查器名称。客户端/模型不能提供任意 JSON path、URL 或文件路径。先确认现有 Agent 快照与版本化配置的最佳落点，再扩展契约。
2. 新 Harness 沿 DSH 原有循环和持久化交换工作。在明确结束时提交已保存候选的引用，使用新版本的 `finish_ref` 语义，避免另造 Go 决策循环或重放时用当前配置选稿。不能仅保留 Node 内存中的 lastDraft。
3. Runtime 从本根任务已提交工具回执读取被允许的原始字符串，验证最新候选、字段摘要、策略/约束修订、租约/fence、取消及未决操作。结束回执与状态恢复沿现有权威持久化路径处理。引用和实际结果可追溯、重复提交幂等，失去回复先核对，不再次调用模型。
4. 业务工具负责内容与格式状态。结构修订阻断、来源待核和实际通过应分清；核心层不能将工具成功、引用匹配或 needs_review 偷换为研究质量通过。以明确的工具输出契约表达可提交性，避免 Runtime 解析特定业务文案。
5. Worker 固定新 Harness 产物与 Runtime execution 版本，安装前完成新旧版本兼容。Console/Futures 只展示产物与状态，不取得执行表写权限。候选草稿已在工具输入中，无需为此新增对象存储体系。

- 用已提交原字符串覆盖 Unicode、换行、尾空格和大稿，最终字节/哈希严格相同；不重新序列化业务 JSON。
