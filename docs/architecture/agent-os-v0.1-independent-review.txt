主要发现（按优先级排列，共 8 项）

1. [P1 / 待设计契约] 运行事件、检查点、调用结果之间没有确定的一致提交与恢复规则。

依据：agent-os-recovery-v0.1.mmd:31 写“保存结果、检查点、事件序号与上下文清单”，第 33 行推进下一步；agent-os-storage-v0.1.mmd:10 同时列事件和检查点。文件没有确定哪份记录是恢复的权威、它们是否在一个数据库事务内发布、检查点包含到哪个事件序号，以及如何提交恢复指针。

失败场景：调用结果已保存，检查点更新一半时进程崩溃；或者检查点指针先推进，关联产物尚未发布。重启若按“最新时间”分别加载各记录，会混合不同进度，遗漏待核对调用或重做已完成步骤。

影响：恢复行为取决于实现者的偶然选择。图中“保存”这个动作可以最终实现成正确事务，但目前还没有证明它具备这些语义。

最小修复：先选一种权威模型：事务化当前状态加审计事件，或事件日志加可重建投影。定义 run_revision、已提交事件序号、checkpoint 对应序号、当前 step、未决 call 和引用集合。数据库内采用单事务/CAS 发布；大产物先完整发布，再引用。任务派发采用持久化待派发记录或可扫描的待执行状态，不能只依赖进程内队列。恢复只从一个已确认的提交边界读取。无需为了这一项立即建设通用事件溯源平台。

证据类型：实际图文检查 + 崩溃次序推演，未做运行验证。Temporal 的官方重放机制以事件历史与确定性命令相符为基础；单独存一个 checkpoint 名称并不等价于拥有该机制。[S1]

2. [P1 / 待设计契约] operation_id 查询与租约声明尚未组成可执行的并发幂等和 fencing 协议。

依据：agent-os-recovery-v0.1.mmd:24 为“查询 operation_id，复用已提交结果或执行”；第 25 行正确要求业务数据与效果回执在可控事务中提交；第 5 行提到 fencing。图没有规定 operation_id 的唯一键/占用、参数绑定、attempt 关系，以及提交端怎样拒绝过期 Worker。

失败场景：A、B 两个 Worker 同时查询到“没有回执”，都执行写操作；或者 A 租约失效后恢复，使用旧权限提交一个不同 operation_id。另一个危险情形是查询不到回执却仍有请求在途，把“没有记录”误判成“确定未执行”。

影响：事务化保存回执不能单独消除并发重复；Runtime 内的逻辑单写者也无法单独阻止旧 Worker 对业务库产生效果。

最小修复：稳定的 operation_id 跨重试保留，attempt_id 每次尝试新建；operation_id 绑定工作区、工具版本和规范化参数哈希。业务提交端用唯一约束或事务性 claim 去重，将业务效果与回执原子提交；提交端还须验证有效 fencing token 或相应的任务/资源版本。租约更新与提交检查的先后关系必须定义，不能只在发出调用时检查一次。对子 Agent 的结果提交同样适用。明确幂等键保留窗口；重试窗口内不得清掉唯一回执。外部服务不支持核对、幂等或 fencing 时，承认能力边界并保留 UNKNOWN，不能声称 exactly-once。

证据类型：实际图文检查 + 并发次序推演。恢复图第 1、2、6 行已正确声明不保证 exactly-once、UNKNOWN 不盲重试和不存在跨库原子事务，本项不把这些已考虑的事项说成遗漏。

3. [P1 / 核心语义缺口] Compact 的引用完整性不能保证有用语义保全，也未定义恢复时旧快照与最新规则的关系。

依据：agent-os-storage-v0.1.mmd:2 要求引用准确版本；第 24 行加载“必需约束”；第 27 行校验必需字段和引用。第 13 行长期记忆只有来源、作用范围、有效期和版本。聊天也已承认程序不能完全判断摘要的语义遗漏。

失败场景：原报告和引用都还在，但“本周样本范围改变，不能直接同比”这句话被摘要删去，后续模型不知道需要回读。任务运行期间用户修正了目标，恢复却继续使用旧的固定规则；反过来，回放历史报告若加载最新修订数据，也会改变当时的依据。

影响：可以做到资料可找回，尚不能保证 Agent 会在正确时点读取它。持久化解决“数据丢失”，没有自动解决“关键语义不再可见”和“资料过期”。

最小修复：将用户约束、未解决问题、证据冲突、口径限制等保存为带来源的结构化任务记录，维护适用范围、优先级、被哪条记录替代以及当前有效修订号；用户变更后在下一安全边界对齐修订号。保留生成摘要时的输入范围和候选摘要版本。区分“恢复同一次执行”“历史回放”“使用最新资料重跑”：分别规定版本冻结与重新授权/规则更新的行为。ContextManifest 应能还原实际发送的内容、顺序与转换结果，而不只是资料 ID 列表。必需信息超出模型预算时显式缩小任务或拆分，不能默默丢弃。用真实长任务验证被压缩后仍能找回关键口径，接受语义保全只能测量、无法仅靠字段校验完全保证。

证据类型：图文中的已声明机制与其可保证性质之间的静态分析；未测试模型 Compact 质量。LangGraph 区分线程检查点与跨线程 Store，有助于分层，但该分层本身不提供本项目的语义保全保证。[S2]

4. [P1 / 待设计契约] GC、新增引用与沙箱产物晋升之间缺少共同的原子性边界。

依据：agent-os-storage-v0.1.mmd:5-7、30 要求根、租约、宽限期；第 11 行列稳定引用和发布状态。agent-os-recovery-v0.1.mmd:25 要求大文件暂存后发布清单；agent-os-v0.1.mmd:31 沙箱提交暂存产物。方向正确，但尚无状态转换和并发规则。

失败场景一：GC 检查无引用并标记待删，随后一个新 ContextManifest 引用该对象，宽限期到后清理器未重新核验就删除。
失败场景二：校验器通过某个沙箱文件，沙箱在正式发布前修改同一路径；数据库最终引用到未校验内容。
失败场景三：事实版本保留了，但没有机器可遍历的事实→证据引用，清理器把原文视作无引用对象回收。

影响：正式报告、恢复检查点或业务事实可能成为悬空引用；“有宽限期”不能解决引用竞争。

最小修复：将产物发布成不可变内容，校验与晋升都绑定内容哈希，沙箱只能写暂存域。定义 staged→validated/published→tombstoned→deleted，或等价状态机。创建引用与进入不可新增引用的删除状态要通过同一元数据事务/CAS 协调；读取期间用有效租约，最终删除前重新核验。建立事实、报告、检查点、上下文清单、记忆到原始证据的显式引用边；保留旧数据版本时一并保留其证据。GC 根应解释为“按策略仍保留的版本”，不能一面把所有历史版本永久列为根，一面承诺自动回收它们。去重对象也需分别检查工作区授权，哈希相同不构成授权。

证据类型：实际图文检查 + 文件替换/GC 并发次序推演，未运行回收器。

5. [P2 / 待设计契约] 模型调用缺少与工具调用同等级的请求、尝试和流式结果状态机。

依据：agent-os-v0.1.mmd:15 有模型调用和流式输出；agent-os-storage-v0.1.mmd:3 已明确模型结果持久化后才允许推动有副作用的动作。这是正确约束，但恢复时序图没有模型调用阶段。

失败场景：模型服务已生成结果并计费，本地只收到半段流后崩溃；重试得到另一个工具计划，旧流随后回到 UI。若没有 attempt 与最终提交的区别，界面会混合两次输出，或系统把旧 attempt 的工具调用当作新结果执行。

影响：即使业务写入幂等，执行历史、用户看到的文本和成本统计仍可能不一致。重试同一提示词不能恢复完全相同的模型输出。

最小修复：保存逻辑 model_call_id、attempt_id、实际请求消息/顺序、模型及可取得的版本信息、参数、工具 schema、服务商请求 ID、实际返回内容和用量。定义一个可被选定的已提交结果，旧 attempt 结果不能继续驱动执行。UI 将未提交流标为临时并按事件序号去重；断线可以重连展示，不能据此宣称供应商会续传生成。已完成结果优先回放，未知结果重试必须计为新尝试及潜在重复费用。Skill、工具实现、运行代码和沙箱镜像固定可复现版本；供应商若只提供会漂移的模型别名，记录此限制。无须也不应假设能取得模型未公开的内部推理状态。

证据类型：图文检查与模型接口故障情形推演，未调用模型服务。总体图实际文件第 16 行止于 R→C→M，缺少聊天版已有的 M→R 返回边；这是小的文档不一致，不单列为结构性缺陷。

6. [P2 / 待设计契约] 取消和子任务仍只有原则，没有父子任务的完成、取消及接管语义。

依据：agent-os-recovery-v0.1.mmd:4 正确区分取消、超时和失败；agent-os-v0.1.mmd:13 有子 Agent；聊天说子 Agent 通过产物提交结果。没有父任务结束后子任务的状态定义。

失败场景：父任务已显示取消或完成，但子 Agent 仍在写入；父进程重启后再次创建同一个子任务，造成双份工作与预算重复；取消请求遇到提交中的调用，UI 立即说“已取消”，之后却出现新数据。

影响：任务状态不可信，子任务失控或成为无人接收结果的孤儿，取消与恢复相互冲突。

最小修复：持久化 parent_run_id、child_run_id、spawn_operation_id、任务修订、预算预留和结果引用。先登记再启动子任务。定义取消请求、停止接新工作、核对在途效果、终态之间的关系，以及父任务结束时对子任务采取等待、取消还是脱离的策略。对于已发生效果如需撤回，只能通过明确的补偿业务操作，不能由 Runtime 假装回滚。

证据类型：图文检查 + 静态并发推演。Temporal 官方同样区分取消请求与执行方接受取消，并有心跳及等待策略；引入该框架也需要选定这些策略。[S3]

7. [P2 / 可靠性范围待定] “落盘”没有对应物理存储、空间不足和备份恢复的最小承诺。

依据：agent-os-v0.1.mmd:2 明确数据库尚未锁定；agent-os-storage-v0.1.mmd:1 允许逻辑区域共用实例；恢复图第 3 行要求持久化失败不报成功。逻辑图不必立即列产品，但当前无法判定确认落盘能抵抗哪些故障。

失败场景：正常杀掉 Worker 能恢复，但磁盘写满导致文件只写一半；或数据库备份与对象目录备份来自不同时点，恢复出的报告引用了未备份对象；本机磁盘损坏后检查点也一起丢失。

影响：进程崩溃恢复、断电持久性、磁盘故障恢复被混成一个“可恢复”的词。用户最在意的原始证据可能只有一份。

最小修复：首版明确支持的故障域与 RPO/RTO 目标；选定事务数据库加不可变对象目录即可，不必拆微服务。定义文件完整性校验、原子发布、磁盘配额/低水位停止采集、数据库及引用对象的一致备份与恢复核验。恢复指针和文件清单需要可一起验证；备份过程也应有 GC 保留租约。以后扩展多机时再增加对应复制和高可用能力。

证据类型：实际设计范围检查 + 故障推演。未检查本机 Docker、磁盘能力或数据库刷盘设置，也未做备份恢复实验。

8. [P2 / 选型与集成风险] 开源候选能力重叠，尚无职责映射证明组合比单一底座更省成本。

依据：agent-os-v0.1.mmd:2 产品未锁定；聊天曾提出 AgentScope 2.0、OpenSandbox、ContextForge、Temporal、Langfuse。总体图没有规定选用其中哪一层功能以及停用哪些默认机制。

失败场景：自建 Runtime、AgentScope 和 Temporal 各自保存一份进度；自建 ContextManager 和框架默认 Compact 同时运行；ContextForge 的重试与 Runtime 重试叠加。升级某一项后恢复状态或幂等参数被适配层丢失。

影响：职责图本身可以保持合理，但组装的系统变成多套状态源，反而使恢复和维护更难。

最小修复：做一页组件职责映射表，选一个运行状态权威、一个 Compact 决策者、一个重试策略拥有者。首版以模块化单体/少量 Worker、一个事务数据库、对象目录和一个 Sandbox 后端运行。先验证所需钩子、版本固定和取消/恢复契约，再决定是否引入独立网关及工作流服务。ToolHub 的通用注册治理与业务能力包是合理划分，但业务事务不会因为包被注册为 MCP 就自动获得恢复保证。

官方核验范围：AgentScope 2.0 文档列有上下文中间件、工作区/沙箱适配、服务持久化；ContextForge 定位是注册与代理治理并自带重试；OpenSandbox 提供 Docker/Kubernetes 路径，本地执行要求 Docker；Temporal 提供自己的事件历史和重放模型。[S1][S4][S5][S6] 这些证明有可复用组件，不证明在本机可安装、互相兼容，或满足上述协议。不能仅据 README 把 AgentScope + OpenSandbox 宣布为已通过的最佳组合。

证据类型：官方文档静态核验 + 职责重叠分析。未做安装、版本兼容、资源成本或授权条款全面审计。

现有方案中合理、应保留的部分

— Runtime 决策运行状态，ToolHub 保持通用、业务实现按能力包注册，适合多个业务；业务数据库和确定性校验继续存在。
— 上下文是工作集，原文、业务事实、长期记忆和执行状态分别存储；检索索引不替代事实库。这一分层符合用户真实需求。
— 接受任务之前持久化、执行调用之前登记意图、业务效果与可控回执同事务，是正确方向。
— 明确 UNKNOWN、取消不等于回滚、不承诺跨系统 exactly-once，避免了常见错误保证。
— 沙箱只产生暂存物，正式事实由业务工具提交；观测系统不作为恢复数据库；逻辑模块不强迫拆成微服务，均合理。
— 不需要在概念图里画出全部 SQL 表或每个异常分支；上述 P1 需要补的是少量决定正确性的契约，不是要求画一张无限复杂的大图。

最小验收场景（建议；全部尚未执行）

A. 提交与恢复：在任务持久化前、调用意图后、业务提交后回执前、Runtime 保存检查点中间分别强制终止 Worker。期望：未接受的任务不报已接受；接受的任务有唯一恢复位置；已完成业务效果不重复；未决调用仍可核对。

B. 并发幂等与接管：重复派发同一个 operation_id，让旧 Worker 暂停、租约过期、新 Worker 接管，再恢复旧 Worker。期望：重复效果为零；过期提交被目标端拒绝；新旧 attempt 的记录可区分。对无法 fencing 的外部模拟服务，结果必须显式 UNKNOWN。

C. 模型断流与版本：模拟收到半段模型流、服务端完成但本地未知、持久化成功后进程退出，再重试/恢复；中途升级工具实现。期望：只选定一个结果驱动动作；旧流不混入新流；已提交结果复用；不静默改用新工具版本；潜在重复费用可记录。

D. Compact 与规则修订：准备长任务，包含样本口径改变、用户撤回旧规则、尚未解决的来源冲突；多次 Compact 后删除进程内上下文再恢复。期望：当前有效规则和限制仍可见，证据可定位；历史回放继续使用原数据版本，最新研究使用显式更新后的版本。不能只测“文件还在”。

E. 引用与 GC：在对象标记待删后并发建立新的 ContextManifest 引用；在沙箱产物验证后修改原路径；保留旧报告再执行 GC。期望：保留引用不悬空；正式提交绑定经过校验的不可变内容；可回溯旧报告；符合策略的无引用暂存物能被回收。

F. 子任务与取消：父任务登记子任务后崩溃、子任务提交时收到取消、父任务已结束但子任务还在运行。期望：无重复 spawn；预算与结果有归属；“取消请求”与“已取消”分别显示；实际已经发生的效果仍有回执。

G. 物理恢复与观测故障：模拟磁盘满、损坏/缺失对象、从数据库与对象备份恢复，同时让 Langfuse 不可用。期望：不虚报提交；引用完整性可检查；任务正确性不依赖观测服务在线。

验收报告应保存每次故障注入位置、输入版本、数据库提交记录、执行次数、恢复结果及未覆盖情况。通过这些场景后，才能将“设计目标”升级为“在指定故障范围和版本下验证的能力”。
