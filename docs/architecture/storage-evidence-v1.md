# 长任务事件存储与证据回查

2026-10-12 实施增量。上游 DSH 仍为 0.2.0-rc.2；新执行协议固定为 `dsh-0.2.0-rc.2-evidence-v1`，已有任务不修改 engine。运行证据的留存不能依赖摘要是否记得来源编号。

## 落盘顺序和所有权

1. DSH 每次桥接调用仅发送自上次调用以来新增的事件。Runtime/Worker 在运行锁和有效 fence 下，将 exchange 意图与首次事件字节一起提交到执行域 `harness_archives`。
2. Worker 将该批次按 UTF-8 边界拆为最多 1 MiB 的不可变段，经 HTTP 上传到 Storage。每段绑定运行引用根；相同字节重传得到相同 SHA-256。
3. 上传批次 manifest，包含各段偏移/长度/hash、完整批次 hash、前一个 manifest、exchange 编号、接收范围与原实例/fence/DSH 索引。每个 manifest 仅描述本批次，避免重复保存全部历史前缀。
4. Storage 确认后，执行域再次检查 fence 和取消，在同一事务写入 manifest/hash 并清除临时 batch。随后才执行该 exchange 的模型请求或工具调用。

未确认的批次是持久化 outbox，不是内存缓存。Worker 中断或上传回复丢失后，重试读取首次落盘字节；不能使用重建 DSH 会话时重新生成的时间戳替换它。旧 fence 可重复上传相同产物，但不能确认、清暂存或提交后续效果。取消时保留尚未确认的原始批次，没有自动删除正式资料的 GC。

已确认的目录行是归档权威；RunState 的 `harness_artifact` 只是最新 manifest 指针。完成回执重放时从目录恢复该指针，覆盖“回执已提交、RunState 尚未保存”的窗口。恢复 DSH 仍使用原有 exchange 请求/响应重放，分段事件不是未经支持的 DSH Session 恢复格式。跨进程原生事件索引可能变化，目录另记接收计数，不伪造源索引连续。

## 模型怎样重新找到资料

`run_recall` 是需要显式绑定的内置工具，新建 Agent 默认勾选，既有 Agent 版本不变。`kind=tools` 按本任务及后代运行树列出已提交的工具回执，支持字面子串检索；`operation_id` 分页读取该回执原文。`kind=events` 列出已确认的事件 manifest，模型可用 `artifact_read` 读取清单与分段。

列表最多 10 项；正文每页最多 1200 个 Unicode 字符；可见运行树最多 128 个；查询有 2 秒 SQL 上限。列表按稳定 ID 排序，是当前调用时的视图，不是时间顺序或跨页快照；新增记录需从第一页刷新。重复同一逻辑调用返回原回执，不偷偷改变重放结果。查询词不会被当作 SQL 通配符。

读取再次校验运行树权限，不能读父级、兄弟或仅共享 Agent 的无关任务。列表不直接包含模型请求和 `run_recall` 自身回执，避免递归膨胀；完整事件仍按运行范围授权。工具结果标为原始资料；来源字段和 fact 标签不构成独立真实性证明。旧 engine 没有新目录，仍按原历史产物协议保存；其工具回执可通过回查工具读取。

## 预算和明确边界

单批原始事件最多 16 MiB，桥接帧最多 32 MiB，Storage 单产物仍最多 4 MiB。单段 UTF-8 字节按清单顺序拼接后才是完整 JSON 数组，单段不保证能独立解析为 JSON。超出预算明确失败，不丢弃已落盘的前序批次。正常结束和 DSH 显式失败都会在新协议下留存最后批次；进程在发出桥接消息前被强杀的内存事件无法承诺已落盘，已提交模型/工具回执仍是恢复依据。

此改动解决累计事件越过 4 MiB 和重复历史前缀导致的存储增长，**不代表无限任务或 DSH 堆内存恒定**。上游内存事件历史仍存在，Node 使用 192 MiB 堆上限，模型步骤/令牌预算仍生效。笔记修订、有效期和正式资料删除策略另行设计，不在本协议内隐式启用。

## 验证

本机真实 PostgreSQL 与官方 DSH：累计约 18.9 MB 事件、40 个批次、16 次 Compact；受控摘要故意省略来源，回查提交后中断真实 DSH 子进程，再由新 fence 恢复，通过回执重新找到原始资料并区分撤回初值、修订实绩与计划。校验全部分段 hash、链、清除已确认暂存和线性存储量；已完成模型调用没有新增尝试。使用受控模型，不冒充真实 DeepSeek 的摘要质量测试。
