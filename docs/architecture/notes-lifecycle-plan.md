# 运行笔记生命周期：下一实施增量

状态：2026-10-12 方案评估，尚未实现。以下来自现有源码与受用户委托的独立评估 agent 的只读复审；评审没有执行测试。分段事件与回查已交付，正式资料仍不启用自动删除。

## 待修正的行为

执行域笔记已与调用回执原子提交。管理 API 支持 supersedes/valid_until，但模型 note_save 不支持；现有 PutDocument 仅检查旧文 kind/scope，多个写入者可能同时生成后继。搜索排除过期和有后继的旧文，尚无完整撤回、冲突处置及理由审计。Knowledge 也使用 recordstore 的普通文档写入，不能把 Runtime 专有状态表变成它的依赖。

## 最小实现约束

- 不改变已有 note_save 的名称、schema、描述；新增显式修订、撤回工具。revision 请求指定 expected_current_id、正文/来源/理由和有效期，继承原 kind/scope，不让模型自报操作者。限制作息字段、metadata 字节和理由长度。
- 所有写入入口使用同一事务规则，包括管理 POST documents 的 supersedes；不能只在模型工具层防并发，管理接口继续绕过。Runtime 专有生命周期操作放在执行域，不让 Knowledge 的普通导入依赖新状态表。
- 先核对原逻辑调用是否已有回执，再检查当前 head。否则成功提交但回复丢失后，会把自己的新版本误判为并发冲突。
- 修订与撤回锁同一目标。锁住不可变原行后，用新的 SQL 语句重新检查后继/撤回/冲突；一条带 NOT EXISTS 的 FOR UPDATE 在等待并发锁时不足以保证不分叉。两个任务、管理 API 与任务同时修订，仅一个允许成功。
- 模型只能修改 scope 非空且等于当前 Agent ID 的笔记。global scope 保持模型只读；父任务可读取后代回执，不因此获得子 Agent 笔记写权限。管理员修改 global 时单独记录可信管理身份。
- 历史分叉原样保留，不按时间自动选赢家；标为需处理的冲突，默认有效搜索不能把分支当唯一当前版本。迁移不盲目建立会因历史分叉失败的唯一后继索引。
- 修订创建新文，旧文不可变。当前 head 过期不返回有效搜索，但可以有理由地修订；撤回留原文及审计，禁止隐式复活；新 head 过期或撤回不能让旧版恢复成当前。
- 历史回读保留原正文、分页字段；生命周期状态放旁置字段，不混进用户 metadata。已提交回执继续原样重放，表示当时读到的内容；新逻辑调用才能查询当前状态。
- 审计和效果、回执同事务。若审计引用 calls，注意 LocalTool 目前在效果之后插入回执，使用正确的延迟约束或调整同事务顺序。

## 必要验收

1. revise/revise、revise/retire、管理 API/模型并发不产生新分叉。
2. 提交前故障没有效果；提交后丢回复、新 fence 重试仅一份修订/撤回及审计。
3. 跨 Agent、global、子 Agent 写入拒绝，合法管理员行为可追溯。
4. 历史分叉、过期、已有回执升级后原资料不变；冲突明确可见。
5. 撤回或新 head 过期后旧版不复活；历史回读标状态，旧回执不变；独立 Knowledge 库继续工作。

此阶段不引入通用事件溯源框架，不自动物理删除笔记、事件或正式原资料。已确认事件的临时 batch 在原子归档确认后释放，是既有 outbox 清理协议，不等同于正式资料 GC。
