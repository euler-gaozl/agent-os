## 实际运行与故障边界

入口：`scripts/Test-ResidentJoint.ps1 -Lifecycle`。从正式 catalog 校验并读取完整发布包，启动实际 Runtime `90e7e9c`、Worker `346c003`、Storage `f1efbf9`、固定 Node 和源码构建的 `dsh-source-639ed015-resident-v2`。Runtime/Worker 与 Storage 使用两个独立的临时数据库及受限角色。Registry、模型和 ToolHub 路由为本地 HTTP 夹具；实际笔记、回执、工作状态与归档由真实服务写入。没有 SQL 修改任务状态、缩短租约或伪造回执来制造通过。

## 数据与资源的生命周期证据

- 故障前后及后续任务完成后，对已完成 calls、model_attempts、历史工作状态、harness_archives 和该任务范围内的笔记逐行比较序列化内容；不是只比较数量。
- 被扣留的第二次工具回复绑定具体 operation ID，通过其 completed 回执关联实际笔记 ID，检查两行哈希不变；两条笔记和两次工具效果均存在。没有把第一条成功调用当作第二条效果的证据。
- 四个故障任务共 66 份 manifest 及其所有分片通过真实 Storage HTTP 回读，核对内容哈希、字节长度、偏移和链关系；历史工作状态 HTTP 返回内容不变，来源回执可通过有界管理 API 读取。
- 取消正在等待的模型时保留一条 `inflight` 模型回执及尝试记录，并出现在管理端 unresolved 查询中。此时子进程已经退出，但未收到供应商结果，不能据此断言供应商是否处理或扣费；不会捏造响应或 token 数。这里没有未决工具效果，不代表非幂等外部工具的不确定效果已验收。
- 专用服务 `TEMP/TMP` 在基线、故障等待、故障退出、每次恢复后和最终检查均为空。这证明本批场景未观察到临时目录残留，**不证明曾创建文件后删除，也不证明所有磁盘缓存都有 GC**。进程内的投影和解析缓存随 Node 退出释放；持久回执、归档、笔记不作为缓存删除。
- `harness_archives.batch` 在本批检查点均已由正常归档确认流程释放，没有人工清空。原始证据、备份、发布包和日志保留；尚未启用自动删除正式资料的策略。
