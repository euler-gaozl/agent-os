# 期货任务页面与错误记录：DSH 实施计划

日期：2026-10-20（Asia/Shanghai）。状态：**已评估，未实施、未部署、未验收**。

用户最新要求：先评估工作量；范围较大则提交计划，由 DSH 实施。错误先记录，按需要手动复盘，**不设置定时任务、自动修复或自动重跑**。本轮只更新交接文档，不改业务包、产品源码或运行服务。

## 1. 结论与工作量

完整需求是中等规模：重复渲染缺陷、信息层级与文案、失败诊断接口、错误记录入口都要处理。单改 CSS 无法解决；也不需要另造一套观测平台。

估算为熟悉 Go/React 的一名开发者、现有环境可用、以本地夹具验证为主的**集中开发工时**，不是 DSH 的墙钟承诺：

| 批次 | 交付物 | 工时 |
| --- | --- | ---: |
| A | 复现并修复重复节点，补动态回归 | 4–8 小时 |
| B | 成功/失败页面布局，修订/来源操作分层，报告锚点隔离 | 4–8 小时 |
| C | Runtime 有界、安全、按应用隔离的诊断投影；Futures 接入 | 8–12 小时 |
| D | 失败记录列表、筛选/分类/导出及手动复盘入口 | 4–6 小时 |
| E | 跨端集成、浏览器验收、候选发布和回滚核对 | 4–6 小时 |
| **首版合计** | **A–E，约 3–5 人日** | **24–40 小时** |

其中 C/D 的完整历史分页与混合版本兼容可能再需 4–8 小时，建议排期预留至 **28–48 小时（约 4–6 人日）**。没有可靠分页、仅筛选最近 100 条的页面不能算完整错误记录交付。

先独立交付 A，再做 B；C 与 B 可并行，D 依赖 C。不要把所有修改堆成一个不可回退提交。

以下另计，不混入首版：Console 管理诊断摘要约 4–8 小时；持久化人工“已复盘/已解决/备注”约 2–3 人日；工具参数拒绝后继续执行的协议修复约 1–2 人日，需单独评估固定执行版本与恢复语义。若实际触及这些范围，先记录差异与依赖，不借 UI 改造悄悄改执行协议。

## 2. 已核对的现状

评估基线为 Futures `84c17f2`；主仓原基线 `c9745eb966`。先核对实际 HEAD、集成 pin 和已安装产物，后续行号可能变化。

### FUX-001：重复的证据关联/修订入口

- 用户截图和本机浏览器都确认了重复节点；一次可访问性快照在截断部分内已有 495 个相同入口。这是显示缺陷，不能解释为“多次修订”。
- `agent-os-futures/web/src/futures.tsx` 中，约 566 行 `TaskEvidenceBinding` 使用 `key={result.id}`；约 695 行同级 `TaskRetainedWork` 使用 `key={result.id + (result.evidence_binding?.manifest_sha256 || "")}`。
- 没有证据关联时两个兄弟 key 相同。源码仅挂载一次，运行包与源文件一致；父级六秒刷新会持续重渲染。这是明确的身份冲突，足以解释节点残留；**仍须用改前/改后同场景浏览器回归确认因果闭环**。
- 修复方向是按组件职责建立稳定且互不相同的 key，并保留任务切换、证据 manifest 变化时必要的状态重置。禁止用随机 key、CSS 隐藏重复区域或定时删 DOM 掩盖问题。
- 依据：[React 的兄弟 key 规则](https://react.dev/learn/rendering-lists#rules-of-keys)。

### FUX-002：失败详情无法说明出错位置

- 豆粕任务 `dd80cadf…`：两次模型请求成功；`kb_search("豆粕")` 和笔记查询成功返回空。
- 第二轮模型随后请求 `kb_search("豆")`；Knowledge 要求至少两个相邻汉字或一个英文词/数字，返回 HTTP 400。
- Runtime 留下 `tool_retryable` 事件，Go 执行桥继续抛错，Worker 终止任务；前端只看见 `upstream request rejected`。后续“库存”查询没有执行。
- 错误不是模型服务连接失败，也不能把“没有搜到资料”说成这次执行失败的原因。
- 对照入口：Knowledge `knowledge/knowledge.go`；Runtime `runtime/tools.go`、`internal/runstate/harness.go`；Worker `worker/dsh.go`、`worker/worker.go`；SDK `serviceclient/client.go`。当前故障涉及共享 Go 执行桥，不应笼统归咎于旧 DSH JavaScript 核心。

### FUX-003：执行完成与研究质量混在一起

- 甲醇任务 `6e4971d0…` 的执行状态为 completed；实际 5 次模型、7 次工具调用。
- 只有 1 个甲醇任务；送检草稿 0、留存原文阅读 0、证据关联为空。结果为 3 个问题、0 条数值事实、3 项非数值说明；报告检查 `needs_review`，13 项提示，`draft-match=not_found`。
- 因此页面上成排的“修订”不是实际草稿版本。应表达“记录已生成；证据仍需核对”，不能把 completed 显示成研究已验证，也不能声称本次运行自动修订过。
- 这些是本机只读观测，私有任务不会随 GitHub 克隆转移。不要把真实结果全文、密钥、数据库、原始回执或用户截图提交到公开仓库。

## 3. 首版用户体验

保持现有 React/TypeScript、Go BFF、配色 token 和服务布局。方向是安静、清晰的中文研究工作台：正文优先，操作集中，状态准确，技术细节按需展开。

### 成功或有报告的页面

1. 顶部只保留品种、研究范围、提交时间和执行状态；证据检查状态独立显示。现有 `created_at` 是提交时间，不能标作生成时间；若需完成时间，必须从真实完成检查点另行投影。
2. 主区直接显示报告：问题、可回答内容、缺失依据。说明编号是引用，不要在同一段内外重复堆相同链接。
3. 报数、原文与具体检查项按需展开；保留逐字来源核对和原始结果导出，不能通过改写或删除报告消除提示。
4. 操作区只有一处：“补充问题，生成新报告”（原修订动作）、“导出记录”、“查看生成过程”。
5. 草稿数为 0 时不显示空的“阶段草稿”大面板；详情内可说明“本次没有保存的检查草稿”。有真实草稿才显示数量、顺序、时间和检查结果；不要自动替代最终稿。
6. 最终报告和每份历史草稿的事实/说明 DOM ID 必须带实例命名空间，点击引用不能跳到另一版本。

### 失败页面

示例信息结构，实际文案必须来自诊断证据：

```text
豆粕 · 供给与库存
执行已停止                         研究范围 / 时间

资料检索未完成
检索词“豆”不符合资料库查询规则，任务在这一步结束。

已完成：2 次模型请求；豆粕正文检索、笔记检索
影响：没有生成最终报告；已有执行记录保留
下一步：查看错误详情，修复后再发起研究

[查看错误详情]   [修改问题并新建研究]
▸ 已保留的资料与生成过程
```

展示查询词仅限诊断白名单允许的本业务短参数；不能从任意异常文本提取并回显请求正文。无法确认具体参数时显示“查询参数不符合要求”即可。

- 失败所在步骤明确标红并说明“未完成”，不能把“执行研究任务”显示成正常完成。
- 诊断暂时读不到时保留原任务状态，提示“错误详情暂时无法读取”，提供只读重读；不能编造原因或重新启动任务。
- 新建研究按钮只打开编辑表单，明确提交后才创建新任务；查看记录、导出和展开详情都不调用模型。

### “源任务”改成什么

它原本指**另一项研究中实际读取过原文的任务**，用于给当前报告补充可回查的历史原文版本；它不是报错来源、模型设置，也不是必填项。

- 常规阅读页不放“为旧报告补充证据关联”。无报告的失败任务不显示此操作。
- 将人工补关联放入“更多 → 关联已有研究资料”，默认关闭。已有关联时显示“使用了哪次研究的资料”，不要反复弹操作框。
- 用研究记录选择器显示品种、日期、结果摘要和可用阅读记录数；只有存在真实阅读回执、同应用、较早且符合后端状态要求的任务可以作为候选。后端必须再次校验，不能只靠前端筛选。
- 手输完整 ID 可作为“按编号查找”的次级入口，不作为默认体验。若首版没有可靠的候选查询接口，保留明确标注的高级入口，不以 N+1 扫描全部任务冒充可用选择器。
- 保存前用具体语言说明：“关联后可回看这次研究保存的原文。保存后不能更换资料来源；原报告保持原样。”确认界面显示将关联的任务与资料数。
- 仍保留同应用检查、原报告/清单哈希、固定版本与不可替换语义；同品种历史记录不是自动证据链，不能自动选择“最近一次”。

## 4. 错误记录与接口边界

### 第一版不另建错误库

Runtime 已有 `runs`、`calls`、`model_attempts`、`events`，是持久化事实源。Futures 不新增数据库、不落 SQL、不读取相邻仓库的执行内部包。第一版只读投影和查询这些记录，刷新、重启页面后仍能查到同一失败。

首版覆盖**已受理任务的失败与效果待核状态**。成功任务中已恢复的错误属于历史诊断；提交前表单/网络错误、浏览器 JavaScript 错误和服务后台故障暂不宣称已经统一收录。UI 缺陷保存在工程问题清单中，两者不要混成任务失败统计。

建议接口（**拟新增，不是已有契约**）：

- Runtime：`GET /v1/apps/{app}/runs/{id}/diagnostics`。
- Futures BFF：`GET /api/tasks/{id}/diagnostics`。
- 如需管理端摘要，另设 control-only `GET /v1/runs/{id}/diagnostics`；Console 链接既有有界 `calls/page`、`calls/record`。
- 错误列表必须由 Runtime 新增兼容的有界分页接口（例如 `/v1/apps/{app}/run-failures`，BFF `/api/task-failures`），不要改变旧列表的数组响应。现有应用任务列表仅返回最新 100 条，没有游标，不能直接作为完整错误记录。
- 时间、品种元数据、步骤和分类筛选须在分页前执行；使用稳定排序、游标及固定查询窗口，游标绑定 app/筛选/窗口。分类在 Runtime 通过通用错误码/阶段投影，不硬编码期货判断。限制扫描与查询预算，返回 `has_more`、截断或覆盖说明；不能前端过滤最近 100 条，也不能逐项发诊断请求做 N+1 全库扫描。
- 统计标注时间范围、是否完整、分页情况；没有全量聚合支持时只写“本页”，不把它叫全库总数。需要的查询索引另行评估，仅由 Runtime 拥有，不能以“无新错误库”推导绝对不可能需要索引迁移。

最小诊断字段：

```text
protocol/version、run_id、failure_version、status
stage、code、safe_message、cause_confirmed
related_event_ids、operation_id（按角色投影）
recommended_action、retry_policy
usage（attempts、unknown_usage_attempts、tokens）
```

`failure_version` 绑定具体失败检查点及内容。旧记录只有可以确切对应时才给“已确认原因”；否则给“最后记录的异常，尚未确定终止原因”。不能简单取最后一个 tool error：它可能已恢复；calls 当前状态也不等于完整历史；事件序号不代表跨事务严格提交顺序。

分类首版控制在少量稳定代码：参数校验、配置/鉴权、下游暂不可用、效果未知、协议异常、预算限制、执行持久化/租约、取消、原因未知。取消与失败分别统计；分类不等于可重试，HTTP 400 不能统一自动重试。

### 权限与数据最小化

- Futures 服务身份和 `app_runs(app,run_id)` 所有权必须双重检查；子任务、关联来源任务和汇总用量不得扩大到跨应用。
- Runtime `runtime/policy.go` 对 ToolHub/Knowledge 有 `/v1/runs/` 的宽泛只读 grant；管理诊断必须像 `calls/page` 一样在前置 guard 限制为 control。
- 业务端只能得到白名单错误代码、业务步骤、安全说明及允许的有界关联。不能返回模型请求/响应全文、供应商 URL、headers、凭证名称、token 或任意原始错误。
- 旧应用详情直接返回 `run.State.Error`、Futures 默认原样渲染的路径需一起处理并回归兼容性；不能只加一个安全面板，却继续在旧字段泄漏异常内容。
- 新 Futures 连接旧 Runtime 或诊断接口返回 404 时，BFF 仍清理/固定映射旧 `task.error`，绝不回退原始异常。旧 Futures 连接新 Runtime 时保持 `error` 的字符串类型与安全通用文案，明确验证两个升级组合。
- 页面中的技术详情也须经过脱敏。查看管理员原始回执需真实管理权限，不能把管理 token 带入前端或做代理提权。
- 只读接口不能写错误状态、改变 run、触发模型、取消、恢复或重试。限页大小、响应字节、查询时限，避免一次扫描全库。
- 诊断与错误列表响应统一 `Cache-Control: no-store`；接口自身失败也返回固定安全消息。SDK `servicehttp.Wrap` 会原样输出未识别 Go error，不能只检查成功投影。诊断读取应保持一致快照，前端结合任务 ID/请求代次/`failure_version` 拒绝迟到或过期响应。

### 手动复盘流程

产品提供“错误记录”：按时间、品种、步骤、分类筛选 → 打开具体错误及依据 → 导出脱敏复盘摘要。频次统计标明范围，不夸大覆盖。

工程侧先用同目录 [问题清单](futures-ux-errors-register-20261020.json) 跟踪：问题编号 → 复现条件 → 责任仓库 → 修复提交 → 回归证据 → 处置状态。每次手动复盘更新，不运行定时任务。

首版不做持久化人工处置状态。如果未来确需在产品里保存“已复盘/已解决/备注”，单独由 Runtime 设计追加式审阅记录、迁移、幂等、并发版本和权限；“已解决”不能改写旧任务真实的 failed 状态，不能复用执行 continuation 表。目前服务身份粒度也不能被虚构为个人审阅身份。

## 5. 工具参数错误的后续修复边界

FUX-004 单独跟踪：明确无副作用、可供模型修正的参数拒绝，应能作为持久化工具拒绝结果返回执行器，而不是让整次任务失去修正机会。

此项**不作为改 UI 顺手修改的内容**。先做离线设计与回归，区分确定拒绝、授权/fence 错误、超时/未知效果、暂不可用；不得把所有 HTTP 400 吞成成功，也不得无界重试。保留旧任务失败状态。

如改变 Worker 编译依赖的 Runtime execution，更新精确模块版本及 vendor，并验证两个 Worker；只升级 Runtime HTTP 不会改变 Worker 内嵌代码。若影响重放可见 Harness 行为，固定新引擎版本，保留旧引擎和回放边界。原 `packs/futures` 的模型、预算、工具、提示词和发布定义保持不变。

| E2 | 已安装候选版本、资产/二进制摘要、健康状态、历史报告/回执不变有记录；可恢复前一完整组合。 |

UI 回归使用明确标为 fixture 的脱敏固定响应，不调用模型、不填虚构市场数据。旧真实任务只读验收；真实付费端到端调用仅在确需验证执行行为时单独安排，不能为了截图反复重跑。

## 7. 测试、发布与回滚

1. DSH 先读主仓及目标仓 `AGENTS.md`、当前部署清单，确认机器、工作目录、Git 脏状态和在途任务；不要复制历史 Windows 命令。
2. 在各服务自己的分支修改。Futures 的 BFF/Web 独立构建；Runtime 的接口/权限与数据库测试由 Runtime 负责；Console 可后置；不要把期货规则放进通用 Runtime/Worker。
3. 按改动运行既有 `go test`、必要 `go vet`，Web `pnpm test`、`pnpm run check`、`pnpm run build`。增加真正渲染父组件、驱动多次状态更新的回归。需要数据库时使用独立临时数据域；skip 不算通过。
4. 当前 Mac 的 `ops/mac-build.mjs` 会覆盖 `local/bin` 和固定 Web 产物，**不能直接当作运行中升级命令**。构建到新的候选目录，记录提交、依赖、Web、二进制与配置模板摘要。
5. 当前 `mac-platform.mjs` 只有 init/configure/start/stop/status，没有通用升级/回滚器。先准备前一完整程序/Web/配置/installed manifest 的回滚包，再进行受控安装；不要只改 SHA 绕过启动校验，不重复 init 数据库。
6. 诊断 API 采用向后兼容新增契约，先装兼容 Runtime，再装依赖它的 BFF/Web；旧 Runtime 时显示诊断不可用，而不是卡死报告。回退通常先退 UI/BFF，再退 Runtime，按具体兼容矩阵确认。
7. 仅改只读诊断 HTTP 时不应顺便升级 Worker；改 execution 才处理精确依赖与双 Worker。保留所有历史 Harness 产物。
8. 发布后查看现有两项任务、验证入口数量、权限与就绪状态；回滚恢复前一完整版本，复核同一批任务。无迁移版本也不能覆盖业务数据。
9. 日常 GitHub Actions 保持关闭；本轮不触发集中 CI，不新增提交触发工作流。源码提交、候选验证、本机安装、研究质量分别记录，不互相替代。
